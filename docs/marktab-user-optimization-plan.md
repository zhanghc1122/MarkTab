# MarkTab 使用者视角问题分析与优化方案

> 调研日期：2026-06-01  
> 对象版本：MarkTab 1.2.5  
> 文档目的：从普通 Markdown 使用者、重度写作者、技术文档维护者和 AI/Agent 协作用户的角度，识别 MarkTab 当前体验短板，并给出可落地的产品优化路线。

## 一、结论先行

MarkTab 当前已经抓住了一个清晰定位：**轻量、Windows 原生、多标签、本地文件优先的 Markdown 编辑器**。它的优势不在“做成第二个 Obsidian/Notion”，而在于比 VS Code 更专注、比 Typora 更适合多文件和 Agent 协作、比大型知识库工具更轻。

但从使用者角度看，当前还有四类明显断点：

| 优先级 | 用户问题 | 当前表现 | 建议方向 |
|---|---|---|---|
| P0 | 找不到内容、改不动内容 | 缺少跨文件搜索；文件内查找替换没有显性入口 | 做“搜索与替换中心”，先解决高频刚需 |
| P0 | “实时预览”预期落差 | 当前是编辑/预览切换，不是真正并排实时预览 | 增加编辑/预览/分屏三态 |
| P1 | AI 或外部工具改稿后不敢合并 | 已有外部变更提示，但没有差异对比与合并 | 增加 diff、接受远端、保留本地、另存副本 |
| P1 | 不敢打开陌生 Markdown | `html: true`、`v-html`、CSP 关闭、文件协议放开 | 增加安全预览模式和信任机制 |
| P1 | 输出交付能力弱 | 只有打印，没有明确 PDF/HTML/图片资源打包 | 做“导出为 PDF/HTML/单文件 HTML” |
| P2 | 长文写作效率不足 | 缺少命令面板、模板、表格/代码块快捷插入 | 做 Markdown 快捷输入和结构化写作辅助 |
| P2 | 可读性和个性化不足 | 设置项少，无暗色主题，无阅读宽度/字体族配置 | 增加主题、阅读宽度、字体、行高配置 |

**推荐路线**：先补齐“搜索、分屏预览、安全模式、导出”四个基础能力，再围绕 MarkTab 的差异化方向做“AI/Agent 协作友好型 Markdown 工作台”。

## 二、外部趋势与用户痛点

截至 2026-06-01，Markdown/笔记工具的用户需求可以概括为五个方向。

### 2.1 用户仍然要本地文件和可迁移

Obsidian 的核心卖点长期围绕“本地 Markdown 文件、隐私、可扩展插件生态”展开；Joplin 也强调开源、同步、端到端加密和 Markdown 笔记。这说明大量用户并不希望内容被锁在云端数据库里，而是希望文件可见、可备份、可被 Git/脚本/AI 工具处理。

对 MarkTab 的启示：**不要追求重型知识库平台化**。应继续坚持本地文件优先，但要把“文件夹工作区、跨文件搜索、外部修改合并、导出归档”做扎实。

### 2.2 搜索已经从“附加功能”变成“入口功能”

Joplin、Zettlr、Obsidian 这类工具都把搜索、过滤、文件管理作为核心体验。用户管理几十个 Markdown 文件时，第一需求不是漂亮预览，而是“我能不能马上找到那段内容”。

对 MarkTab 的启示：当前目录树只能解决“我知道文件在哪”的场景，不能解决“我只记得内容关键词”的场景。跨文件搜索应提升到 P0。

### 2.3 AI 写作正在改变编辑器预期

Notion AI、Obsidian 社区插件、VS Code/Copilot 类工具已经让用户习惯了“选中文本后解释、改写、总结、生成大纲”的交互。即使 MarkTab 不内置云端 AI，也应该给 AI/Agent 协作留出产品接口。

对 MarkTab 的启示：MarkTab 已有“外部修改检测”和“非 dirty tab 静默刷新”，这是很好的基础。但使用者真正需要的是：看清 AI 改了什么、能局部接受、能回滚，而不是只知道文件变了。

### 2.4 输出交付仍是 Markdown 编辑器的硬需求

Typora、Zettlr 等工具都强调导出能力，用户写 Markdown 的最终目的往往是交付 PDF、HTML、文档包或可分享页面。纯打印只能覆盖一部分场景，不能替代“可命名、可复现、带资源处理的导出”。

对 MarkTab 的启示：导出不是低频装饰功能，而是写作闭环。尤其对于技术文档用户，PDF/HTML 导出会直接影响是否能把 MarkTab 当主力工具。

### 2.5 安全和隐私要求更高

Markdown 预览通常涉及 HTML 渲染、外链、本地图片、脚本或图表渲染。MarkTab 当前为了兼容预览关闭 CSP，并允许广泛本地资源访问；这对可信文档很方便，但对下载的陌生 Markdown、AI 生成的 Markdown、第三方仓库文档都存在风险。

对 MarkTab 的启示：用户不一定懂 CSP 和 XSS，但他们能理解“信任此文件夹”和“安全预览”。应把安全能力产品化，而不是只停留在技术配置里。

## 三、当前产品体验诊断

### 3.1 当前优势

| 能力 | 用户价值 | 保留建议 |
|---|---|---|
| 多标签编辑 | 同时处理多个 Markdown 文件 | 继续强化标签管理、拖拽排序、关闭恢复 |
| 目录树与收藏目录 | 适合项目文档、仓库文档 | 增加搜索、过滤、最近打开分组 |
| Mermaid/draw.io 预览 | 对技术文档用户有吸引力 | 增加错误定位、图表导出、缩放体验 |
| 图片粘贴保存到 `.assets` | 降低写文档插图成本 | 增加重命名、压缩、相对路径策略 |
| 外部修改检测 | 适合 Git/Agent/脚本协作 | 扩展为可视化 diff/merge |
| Windows 文件关联 | 降低打开成本 | 增加命令行参数与最近窗口行为说明 |

### 3.2 主要问题

#### 问题一：用户找内容的成本高

当前 MarkTab 有目录树和最近目录，但缺少跨文件搜索。用户面对一个项目文档目录时，必须先知道文件名，再逐个打开查找。即使 CodeMirror 已接入 `searchKeymap`，普通用户也看不到“查找/替换”的显性入口。

**优化目标**：让用户在 3 秒内从关键词定位到文件、标题、行号和上下文。

#### 问题二：“实时预览”表达与体验不一致

README 写的是 Live preview，但当前主界面是编辑模式和预览模式切换。用户理解的实时预览通常是左写右看，或者至少能同时看到编辑和渲染结果。

**优化目标**：提供 `Edit / Split / Preview` 三态，并记住用户偏好。

#### 问题三：外部修改提示还不够可决策

现有 conflict banner 能告诉用户文件被外部修改或删除，但用户最关心的是“到底改了哪里”。没有 diff 时，用户只能全量 reload 或保留本地，决策成本高。

**优化目标**：把外部修改从“危险提示”变成“可审阅变更”。

#### 问题四：安全模型对普通用户不可见

`markdown-it` 开启 HTML，预览使用 `v-html`，Tauri 配置中 CSP 为 `null`，asset protocol 允许范围较宽。技术上有兼容性原因，但从产品上需要给用户一个可理解的边界。

**优化目标**：默认安全、按文件夹信任、风险可解释。

#### 问题五：导出链路不完整

当前有 Print，但没有菜单式的“导出 PDF/HTML”。用户需要交付文档时，会期待可选择纸张、页边距、是否包含目录、是否内嵌图片和样式。

**优化目标**：把“写完”之后的交付动作产品化。

## 四、优化方案

### 4.1 P0：搜索与替换中心

跨文件搜索是 MarkTab 从“单文件编辑器”升级为“项目文档工作台”的关键。

| 功能 | 说明 | 交互建议 |
|---|---|---|
| 文件内查找 | 支持普通文本、大小写、全词、正则 | `Ctrl+F` 打开顶部搜索条 |
| 文件内替换 | 单个替换、全部替换、正则替换 | `Ctrl+H` 展开替换栏 |
| 跨文件搜索 | 搜索当前文件夹、收藏目录、最近目录 | 侧边栏新增 Search tab |
| 搜索结果上下文 | 展示文件名、行号、命中片段 | 点击跳转并高亮 |
| 过滤范围 | `*.md`、排除 `.assets`、排除隐藏目录 | 搜索框下方轻量过滤 |

**实现建议**：前端先基于 Tauri fs 递归读取 Markdown 文件，建立按需搜索；后续再做增量索引。第一版不必上全文索引库，避免过早复杂化。

### 4.2 P0：编辑/分屏/预览三态

当前模式切换建议改为三段式控制：

| 模式 | 适用场景 |
|---|---|
| Edit | 专注写作、屏幕窄、长文本输入 |
| Split | 技术文档、图表、表格、图片密集内容 |
| Preview | 审稿、阅读、打印前检查 |

**关键体验要求**：

- Split 模式下编辑和预览滚动联动。
- 预览错误不应吞掉内容；Mermaid/draw.io 出错时显示错误块和源代码。
- 记住每个用户的默认模式，但不要按文件记太多状态，避免状态复杂。

### 4.3 P1：外部修改 diff/merge

MarkTab 的差异化机会在这里。很多 Markdown 用户已经在用 Git、AI agent、脚本或同步盘改文件。现有“外部变化检测”可以升级为变更审阅。

建议新增 `Review external changes` 面板：

| 操作 | 用户理解 |
|---|---|
| View Diff | 看外部版本和当前编辑版本差异 |
| Accept Disk | 接受磁盘版本 |
| Keep Mine | 保留当前版本 |
| Save Both | 当前版本另存为冲突副本 |
| Copy Patch | 复制差异，便于给 AI/开发工具处理 |

**实现建议**：第一版做行级 diff；后续再做 word-level diff。不要一开始做复杂三方合并，先解决“看清楚改了什么”。

### 4.4 P1：安全预览与信任机制

建议把安全分为三档，让普通用户能理解。

| 模式 | 行为 |
|---|---|
| Safe Preview | 默认禁用原始 HTML、脚本、危险协议和未知本地资源 |
| Trusted Folder | 对用户主动信任的文件夹启用完整 Markdown 能力 |
| Developer Mode | 允许 HTML、draw.io、Mermaid、广泛本地资源访问，并显示风险提示 |

**实现建议**：

- 默认 `html: false`，仅在信任目录中开启。
- 预览 HTML 前增加 sanitizer。
- 外链点击前区分 `http/https/file/data` 协议。
- Tauri asset scope 从 `["**"]` 收窄到当前文档目录、`.assets` 和用户信任目录。
- 设置页增加“Trusted folders”管理。

### 4.5 P1：导出 PDF/HTML

建议新增 `Export` 菜单，先做三种输出：

| 输出 | 用户价值 |
|---|---|
| PDF | 汇报、归档、合同/方案交付 |
| HTML | 内部网页、轻量分享 |
| Self-contained HTML | 图片和样式内嵌，便于单文件发送 |

**导出选项**：

- 纸张：A4 / Letter
- 方向：Portrait / Landscape
- 是否包含目录
- 是否显示代码行号
- 是否内嵌图片
- Mermaid/draw.io 是否转为 SVG

第一版可复用现有 print 渲染管线，但要从“调用打印机”改为“生成明确文件”。

### 4.6 P2：Markdown 快捷输入

建议提供轻量命令面板，而不是复杂块编辑器。

| 输入 | 插入内容 |
|---|---|
| `/h1` `/h2` `/h3` | 标题 |
| `/table` | Markdown 表格模板 |
| `/code` | 代码块 |
| `/mermaid` | Mermaid 模板 |
| `/drawio` | draw.io 引用模板 |
| `/task` | 任务列表 |
| `/toc` | 文档目录占位 |

**原则**：保持 Markdown 原文可见，不引入私有块格式。

### 4.7 P2：主题与可读性

设置页建议从“技术参数”升级为“写作环境”。

| 设置 | 建议 |
|---|---|
| Theme | Light / Dark / System |
| Editor Font | Monospace 字体选择 |
| Preview Font | Sans / Serif / System |
| Reading Width | 680 / 800 / 960 / Full |
| Line Height | Compact / Normal / Relaxed |
| Accent Color | 保留品牌紫，但不让全界面过度紫色化 |

暗色主题优先级应高于更多装饰性 UI，因为它直接影响夜间写作和长时间阅读。

## 五、路线图

### 第一阶段：补齐主力编辑器刚需（1-2 个版本）

| 任务 | 交付标准 |
|---|---|
| 文件内查找/替换显性 UI | `Ctrl+F/Ctrl+H` 可发现、可关闭、可高亮 |
| 跨文件搜索 MVP | 当前目录下搜索 Markdown，展示文件/行号/片段 |
| Edit/Split/Preview 三态 | 分屏模式可用，滚动基本联动 |
| 导出 PDF MVP | 可选择路径并生成 PDF |

### 第二阶段：形成 MarkTab 差异化（2-3 个版本）

| 任务 | 交付标准 |
|---|---|
| 外部修改 diff | 能看行级差异并选择处理方式 |
| 安全预览模式 | 默认安全，可信目录可放开 |
| HTML/self-contained HTML 导出 | 图片路径和样式可正确处理 |
| 暗色主题 | 编辑器、预览、侧边栏一致 |

### 第三阶段：提升写作效率与生态适配

| 任务 | 交付标准 |
|---|---|
| `/` 命令面板 | 常用 Markdown 模板可快速插入 |
| 模板库 | 新建文档可选择会议纪要、技术方案、周报等模板 |
| AI/Agent Hook | 暴露“选区上下文、当前文件路径、保存后刷新”的稳定接口 |
| Git 状态提示 | 文件树展示 modified/untracked，可打开外部 Git 工具 |

## 六、验收指标

| 指标 | 目标 |
|---|---|
| 搜索可用性 | 1000 个 Markdown 文件内关键词搜索首屏结果小于 1 秒 |
| 分屏体验 | 编辑输入到预览更新小于 300ms |
| 外部修改处理 | 用户能在 2 次点击内查看 diff，并在 1 次点击内选择处理方式 |
| 导出稳定性 | 图片、代码块、Mermaid 图在 PDF/HTML 中正确显示 |
| 安全默认值 | 未信任文档不执行原始 HTML/脚本，不访问任意本地路径 |
| 新用户上手 | 首次打开空界面能在 10 秒内理解“打开文件/打开文件夹/新建文件” |
